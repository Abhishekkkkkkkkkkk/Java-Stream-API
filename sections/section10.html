Stream Internals & Architecture

Spliterator, Pipeline, Sink — how the JVM processes streams

Spliterator — The Engine of Stream Splitting

A Spliterator (Splittable Iterator) powers both sequential traversal and parallel decomposition. It knows how to split a data source into halves for parallel processing.

Java — Spliterator 
Spliterator<String> sp = List.of("a","b","c","d").spliterator();
sp.estimateSize();     // 4
sp.characteristics(); // ORDERED | SIZED | SUBSIZED

// tryAdvance — process one element
sp.tryAdvance(System.out::println); // "a"

// trySplit — split into two halves for parallel
Spliterator<String> half = sp.trySplit(); // half has "b", sp has "c","d"

// Characteristic flags (what the Spliterator guarantees)
// ORDERED   — encounter order preserved
// DISTINCT  — no duplicate elements
// SORTED    — elements in sorted order
// SIZED     — exact element count known upfront
// NONNULL   — no null elements
// IMMUTABLE — source cannot be modified during traversal

Lazy Execution — How the Pipeline Really Works

Intermediate operations build a linked chain of stages. No data flows until the terminal operation "pulls" through this chain element-by-element.

Java — Pipeline Execution Trace 
// Pipeline: [1..10] → filter(even) → map(×2) → limit(3) → toList
List<Integer> result = IntStream.rangeClosed(1,10)
    .filter(n -> n%2==0)
    .map(n -> n*2)
    .limit(3)
    .boxed()
    .collect(Collectors.toList());
// Output: [4, 8, 12]

// Internal element-by-element execution:
// 1 → filter(1%2≠0) ❌ skip
// 2 → filter(2%2=0) ✅ → map(2×2=4)  ✅ → limit(1/3)
// 3 → filter(3%2≠0) ❌ skip
// 4 → filter(4%2=0) ✅ → map(4×2=8)  ✅ → limit(2/3)
// 5 → filter(5%2≠0) ❌ skip
// 6 → filter(6%2=0) ✅ → map(6×2=12) ✅ → limit(3/3) STOP!
// Elements 7,8,9,10 are NEVER processed — lazy evaluation wins!
🔍

Key Optimization Insight

Place filter() before map() to reduce elements for expensive transformations. Place limit() early for maximum short-circuiting on infinite or large streams.
