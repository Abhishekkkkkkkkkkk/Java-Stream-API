Interview Questions & Answers

Beginner to advanced — with detailed, interview-ready explanations

🟢 Beginner Questions

EasyQ1: What is the difference between Stream and Collection?
Answer

A Collection stores data in memory and can be iterated multiple times. A Stream is a pipeline for processing data — it does not store data, is lazy (executes only when a terminal operation fires), and can only be traversed once. Collections are eager (data computed upfront); Streams are lazy (computed on demand).

EasyQ2: What is lazy evaluation in Streams?
Answer

Intermediate operations like filter() and map() don't execute when chained — they build a pipeline description. Execution only begins when a terminal operation is called. This enables short-circuit evaluation (e.g., findFirst() stops after finding one match) and avoids processing unnecessary elements, saving significant computation on large datasets.

EasyQ3: Name five terminal operations and five intermediate operations.
Answer

Terminal: collect(), forEach(), reduce(), count(), findFirst(), anyMatch(), min(), max(), toArray().

Intermediate: filter(), map(), flatMap(), sorted(), distinct(), limit(), skip(), peek(), mapToInt().

🟡 Intermediate Questions

MediumQ4: What is the difference between map() and flatMap()?
Answer

map() applies a 1-to-1 transformation — one input element produces exactly one output element. If the mapper returns a Stream, you get Stream<Stream<T>> — nested streams.

flatMap() applies a 1-to-many transformation and flattens the result. The mapper must return a Stream, and flatMap merges all those sub-streams into one flat stream. Use it to work with nested collections or when each element maps to multiple results.

Java 
List<List<Integer>> nested = List.of(List.of(1,2), List.of(3,4));
nested.stream().map(Collection::stream);    // Stream<Stream<Integer>> ❌
nested.stream().flatMap(Collection::stream); // Stream<Integer>         ✅
MediumQ5: What is the difference between findFirst() and findAny()?
Answer

findFirst() always returns the first element in encounter order — deterministic, even in parallel streams. findAny() returns any element — non-deterministic, but potentially faster in parallel streams because whichever thread finds an element first can return immediately. In sequential streams, both behave identically.

Use findFirst() when order matters; use findAny() in parallel when you just need any result quickly.

MediumQ6: What is the difference between reduce() and collect()?
Answer

reduce() performs immutable reduction — it combines elements into a single value via a BinaryOperator, producing no intermediate mutable containers. Good for numeric aggregation, finding max/min, or string concatenation without needing a container.

collect() performs mutable reduction — it accumulates elements into a mutable container (ArrayList, HashMap) using a Collector's Supplier + Accumulator + Combiner. It's more efficient for building collections because it avoids creating many intermediate objects as immutable reduce does.

MediumQ7: When would you use orElse() vs orElseGet()?
Answer

orElse(value) always evaluates the argument — even if the Optional is present. orElseGet(supplier) is lazy — the Supplier is only called if the Optional is empty. Always prefer orElseGet() when the default is expensive to compute (DB query, network call, complex object creation). Use orElse() only for cheap constant defaults like orElse("unknown").

🔴 Advanced & Tricky Questions

HardQ8: What does allMatch() return on an empty stream and why?
Answer

allMatch() on an empty stream returns true — this is called vacuous truth. The statement "all elements satisfy predicate P" is vacuously true when there are no elements to violate it. allMatch() needs at least one element that returns false to return false — with zero elements, that can never happen. Similarly: noneMatch() on empty = true; anyMatch() on empty = false.

TrickyQ9: What does this code print, and why?
Java — Predict the output 
Stream.of("a","b","c")
    .peek(s -> System.out.print("p1:"+s+" "))
    .filter(s -> !s.equals("b"))
    .peek(s -> System.out.print("p2:"+s+" "))
    .count();
Answer

Output: p1:a p2:a p1:b p1:c p2:c

This reveals the element-by-element lazy execution: "a" passes both peeks; "b" passes p1 then fails filter so p2 is never called; "c" passes both peeks. Elements traverse the full pipeline one at a time, not stage by stage across all elements.

HardQ10: Explain the three-argument form of reduce().
Answer

reduce(identity, accumulator, combiner) — the combiner is only used in parallel streams to merge partial results from different threads. This form also allows reduction when the output type differs from the element type.

Java 
// Count total characters across all strings (int output, String input)
int total = Stream.of("hello","world","java")
    .reduce(0,
        (sum, s) -> sum + s.length(),  // accumulator: int+String→int
        Integer::sum);                   // combiner:    int+int→int (parallel merge)
// 14
AdvancedQ11: What is a Collector and how does it work internally?
Answer

A Collector<T,A,R> is defined by four components:

  • Supplier<A>: Creates a new mutable result container (e.g., ArrayList::new)
  • BiConsumer<A,T> accumulator: Adds an element to the container (e.g., List::add)
  • BinaryOperator<A> combiner: Merges two containers in parallel (e.g., List::addAll)
  • Function<A,R> finisher: Optional final transformation (e.g., wrapping in Collections.unmodifiableList())

Collectors.toList() implementation: Supplier=ArrayList::new, Accumulator=List::add, Combiner=list1 adds all of list2, Finisher=identity (no transformation).

AdvancedQ12: Why should you avoid using parallel streams with stateful operations?
Answer

Stateful operations like sorted() and distinct() must see ALL elements before producing any output. In parallel streams, each thread processes its chunk independently, but stateful operations require barrier synchronization — all threads must stop and merge their results before proceeding. This:

  • Eliminates the parallelism benefit for that operation
  • Adds significant synchronization overhead
  • Can cause unpredictable ordering if multiple stateful ops are chained

For sequential streams, stateful operations are perfectly fine. Use them with parallel streams only when you've profiled and confirmed benefit.

TrickyQ13: Can you explain why Stream.of(1, 2, 3).reduce(0, Integer::sum) is different from Stream.of(1, 2, 3).reduce(Integer::sum)?
Answer

The two-argument form reduce(0, Integer::sum) takes an identity value and always returns int (type T). Since the identity is provided, there is always a result even on an empty stream (returns identity=0). The one-argument form reduce(Integer::sum) has no identity, so it returns Optional<Integer> — empty Optional if the stream is empty, avoiding the need to define an identity value.

AdvancedQ14: How would you handle checked exceptions in stream lambdas?
Answer

Lambda functions used in streams cannot throw checked exceptions directly because the functional interfaces (Function, Predicate etc.) don't declare checked exceptions. Common solutions:

Java — Three approaches 
// 1. Wrap in try-catch inside lambda
stream.map(s -> { try { return process(s); } catch (IOException e) { throw new RuntimeException(e); }});

// 2. Utility wrapper method (cleaner)
static <T,R> Function<T,R> wrap(CheckedFunction<T,R> fn) {
    return t -> { try { return fn.apply(t); } catch(Exception e) { throw new RuntimeException(e); }};
}
stream.map(wrap(this::riskyOperation));

// 3. Use a library like Vavr or Lombok's @SneakyThrows
TrickyQ15: What is the output of Stream.of("a","b","c").parallel().forEachOrdered(System.out::print)?
Answer

Always prints: abc — forEachOrdered() guarantees encounter order is maintained even in a parallel stream. This is unlike forEach() on a parallel stream which may print in any order (e.g., bac, cab, etc.). The trade-off is that forEachOrdered() reduces parallelism benefit since threads must synchronize to maintain order.
